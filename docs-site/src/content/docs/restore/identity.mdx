Selected Tenant settings, Authentication, External identities and Governance policies can be restored individually after an exact preview and a separate confirmation. Confirmation belongs to that restore run, tenant, signed-in admin and backup source. A new preview requires its own confirmation. If an earlier restore recreated a policy with a new ID, replacement previews and updates use that saved target mapping. [Users and groups](#users-and-groups) have limited directory restore subsets. App registrations support nonempty displayName and description updates through their [individual application review](#app-registrations-enterprise-apps-and-consent). All other Entra ID types and every Defender type remain backup-only. Cross-tenant copy and bulk restore of the new types remain refused. A documented Microsoft Graph API does not enable restore in TenuVault.

Conditional Access and Intune retain their existing restore behavior. See [Restore modes and assignments](/restore/modes/) for those policies.

## Protection before enabling restore

The restore safety boundary requires the signed-in admin for the connected tenant and registration. A Backup Reader, an app-only token or an unreadable token cannot write a new type. Missing write permissions require adding restore access from Services in Settings and signing in again.

Tenant settings restore access includes Application.Read.All to check token lifetime policy bindings. It grants no application writes. Each operation runs only the protections that its closed payload can affect. The seven enabled subsets cannot remove protected identities, administrator roles, authentication methods or the connected registration. Token binding and non-default policy checks still run, and incomplete evidence blocks the affected policy.

The boundary protects the signed-in admin's own account, roles and authentication methods, designated recovery accounts and the connected TenuVault registration and enterprise app. Removing the last Global Administrator or Privileged Role Administrator is refused. An unresolved safety reference blocks the affected policy.

Members, owners and collection entries are added by default. Removing existing entries requires a choice for that individual policy. Consent grant changes merge scopes by default. Consent grants and role assignments from imported backups are refused. New Entra ID and Defender types cannot be copied to another tenant.

## Review recovery accounts and saved results

Open **Settings > Storage and recovery** and choose the restore history tenant. **Identity restore safety** shows the recovery account object IDs saved for that tenant. Enter one ID per line and select **Save recovery accounts**. TenuVault verifies that each is an enabled cloud member account before saving the choice on this device. An empty list designates no additional recovery accounts. The signed-in admin, connected registration and enterprise app remain protected.

## What partial means

Microsoft Graph offers no transaction across policies. A restore can finish some steps before another is blocked, cancelled or unanswered. A partial result records each policy's state and its dependencies. It does not promise that earlier changes were rolled back.

The journal captures only the objects a run touches before writing them. It binds the run to its tenant, signed-in admin and reviewed plan. A tenant change since preview requires a new preview. Created IDs and typed reference mappings persist across runs and are loaded before preview. Execution validates them again against the current journal. The journal retains the latest 1,000 settled runs, every unresolved run and every mapping independently. Dependencies with missing prerequisites or cycles are blocked for review. Replaced IDs referenced by Intune or Conditional Access require review of those policies. The reference scan keeps matches as it reads each policy and avoids script, image and secret sub-reads. Its overall budget is 500 requests, 30 seconds and 16 MiB of response data. The scan checks its read access before contacting Intune or Conditional Access. Missing access, cancellation, a failed read or any exceeded budget produces an incomplete-scan warning, never an empty-reference assurance. A completed configuration write can therefore still be reported as partial when unrelated reference reporting is unavailable.

A failed check before a mutation is sent is recorded as failed-before-send and permits a fresh preview. The send marker is saved immediately before the mutation request. A crash after that marker is conservative: the outcome stays uncertain even if the request had not yet left the device. An unanswered write must be read back before any retry. A matching object must have an unambiguous identity and match the sent properties. An empty or ambiguous lookup leaves the outcome uncertain, with no second create. Changing recovery accounts does not prevent read-only reconciliation. Current recovery protections apply before any later write. Restarting resumes from saved steps. Journal captures reject credential properties and credential values.

## Never restored

Secrets, passwords, OATH seeds, synchronization flags, domains, devices, Microsoft-managed and built-in objects are never recreated or overwritten by the new writer. Organizational contacts and Microsoft attack simulation content have no parent write contract. Attack simulation and training campaigns are never restored. Only the individually admitted directory subsets below can be restored. Privilege assignments remain blocked.

Open a backup in Restore and expand its policy type. Enabled policies have **Review this configuration** beside their entry. Choose replacement of an existing policy or recreation of a missing policy, preview the exact changes, then select **Confirm and restore this policy**. Tenant singletons can only be replaced in place. Changing the operation or removal choice discards the preview. These controls are separate from selection and restore all.

| Type | Verified subset | Own confirmation |
| --- | --- | --- |
| Token lifetime policies | Create or update unbound, non-default Version 1 AccessTokenLifetime definitions | sign-in-policy |
| Activity-based timeout policies | Create or update non-default Version 1 ApplicationPolicies timeout definitions | sign-in-policy |
| Authentication flows | Replace self-service sign-up state | authentication |
| Company branding | Replace or clear the default username hint | configuration |

The matrix below records the final availability of every type and operation. Unsupported nested properties and child configuration are refused. The branding review explicitly restores only the default username hint from a full backup. Other branding fields, streams, layout and localizations stay as configured in the tenant. Clearing a username hint uses a null reset. Other policy types still refuse unsupported writable properties and child configuration.

Organization notification emails and phones, and the privacy profile, are never restored in 0.6. [Microsoft requires Organization.ReadWrite.All](https://learn.microsoft.com/en-us/graph/api/organization-update?view=graph-rest-1.0) for these changes, and TenuVault never requests that permission. Branding uses the separate least-privileged [OrganizationalBranding.ReadWrite.All permission](https://learn.microsoft.com/en-us/graph/api/organizationalbranding-update?view=graph-rest-1.0).

Permission grant policy metadata remains blocked after a live PATCH refusal (HTTP 400). Authorization policy, security defaults and authentication methods remain blocked. Their live verification used identical values only. Effective authentication-method targeting and usable methods for the signed-in admin are not yet established. Security defaults also have an unresolved least-privilege permission discrepancy. Admin consent request policy remains blocked because the lab's original zero-day duration does not satisfy the staged builder's restore-original contract. Directory settings and authentication contexts lack a verified safe lab fixture and write grant. Federation, certificate PKI, credential restrictions, token issuance, claims mapping and home realm discovery remain blocked. Domains, synchronization flags, credentials and hardware token seeds are never written.

The lab used an app-only adapter with an explicit path allowlist. It does not verify the product's signed-in actor, confirmation or journal boundary, which are covered by injected-fetch tests. Prefixed policies are removed in finally blocks. Singleton originals are saved outside the repository before changing them, restored and read back. Restoring a singleton original uses bounded retries with read-back reconciliation, including after a refused or lost recovery response. Final cleanup retries unresolved singleton recovery before any other mutation. A pending recovery file is kept until the original is verified and prevents another write run. Non-personal singleton originals and verified end values are recorded in a private run artifact outside the repository. Microsoft Graph can take time to propagate a create, update or delete; verification re-reads before deciding whether the result is confirmed. A failed or unanswered write is never treated as a promise of rollback. Notification values are never changed in the lab.

## External identities, Governance and Defender

Three additional types have live-verified subsets. Each uses the signed-in admin, an exact preview, the touched-object journal and its own confirmation. No type is included in restore all, Copy to Tenants or cross-tenant copy.

| Type | Enabled operation and closed subset | Own confirmation | Lab evidence |
| --- | --- | --- | --- |
| CrossTenantAccessPolicy | Update the parent displayName only, projected from a full backup | cross-tenant-access | Changed name read back; original restored and independently verified. An initial recovery refusal and stale replica were detected by the fresh audit; retrying the original succeeded. |
| AccessPackageCatalogs | Create unpublished, externally hidden catalogs, or update user-managed catalogs already in that state; displayName and description only with those fixed safety values | configuration | Create/read/change/restore/delete matched. Microsoft documentation and the current permission model confirm the endpoints; the local Graph index has no exact catalog write entry. Explicit live evidence admits these two contracts without marking the index as matched. |
| AccessReviewPolicy | Update isGroupOwnerManagementEnabled only (beta) | configuration | Changed ownership flag read back; original restored and independently verified. No review was created or run. |

Full access review backups restore only isGroupOwnerManagementEnabled; their read-only displayName and description stay out of the write. Confirmation remains bound to the full source backup. Unknown source properties are refused.

Catalog resources, packages and assignments are excluded. A backup with nonempty resources is refused. Read-only catalog type and timestamps and empty resource lists do not become write properties. Null uniqueName and serviceManagementReference fields are omitted; configured values require a reviewed builder and are refused. Service-default catalog backups cannot be restored. Published, externally visible, service-default or unresolved live catalog types cannot be updated. Cross-tenant defaults, partners, cloud endpoints, trust and synchronization settings stay as configured, and their restore paths remain blocked because the signed-in admin's tenant relationships cannot be resolved safely.

The other staged operations remain blocked with specific reasons in the app and matrix:

* Custom user-flow attributes: the approved prefixed create returned HTTP 400 AADB2C99039. Update and restore round trips could not be established.
* External-identities leave flag: the identical value was written and read successfully, but changing guest access was never tested or approved.
* Lifecycle workflow settings: reading the original returned HTTP 403 Access denied. No write was sent, and schedule changes remain unverified.
* Lifecycle workflows: workflow writes are outside the approved lab scope. Creation also needs recycle-bin-first recovery. Disabled metadata candidates have injected-fetch evidence only.
* Defender custom detection rules: disabled creation succeeded, but Graph expanded detectionAction with null fields, empty alert mappings and empty automated-action collections. Exact read-back and restore reconciliation did not match the closed candidate, so create and update remain blocked. The prefixed rule was deleted. Response actions and activation are never sent.

Automatic-result review definitions remain blocked because disabling result application alone does not prevent scheduling or notification effects. Provider and connector secrets must be entered again; secret-free creation is not verified. Attack simulations and their content are never restored. Built-in roles and attributes stay protected. Administrative units require recycle-bin-first recovery. Attribute sets and definitions cannot satisfy the approved delete-cleanup lifecycle. PIM rules, sensor settings, workbook discrepancies and notification-bearing policies retain their specific matrix reasons.

The app-only lab adapter cannot certify the desktop delegated sign-in or isolate permission alternatives. Production-service tests independently exercise generated area scopes, immutable confirmation, the journal and applicable guards. Recovery retries only saved originals. It requires repeated matching singleton reads and does not accept a stale original after a definite write refusal. Cleanup honors bounded Retry-After delays for read and delete throttling. A fresh-token audit compares saved originals and confirms no prefixed objects. Workflow settings remained unreadable and were never changed; equality of that unavailable singleton could not be verified.

## Users and groups

Open an owned backup, expand Users or Groups and select **Review directory restore**. This flow is separate from restore all, Copy to Tenants, drift revert, imports and cross-tenant copy. It runs as the signed-in admin, never the Backup Reader.

Choose **Directory object** first. Missing objects are checked against deleted items before recreation. Recycle recovery remains blocked until recovered relationships and account state can be inspected safely. TenuVault never skips the recycle bin to create a second identity. A missing object outside deleted items can be recreated. A recreated user starts disabled with a fresh random password that is never retained, logged or shown. Set up sign-in and enable the account separately in Entra.

A new object ID breaks references that still target the old ID, such as policy targets and external integrations. Confirmed mappings are saved for later directory relationship previews on this device. Review Intune and Conditional Access references separately. If reference reporting is unavailable, the result is partial, not an assurance that no references exist. Recreating an application also changes its app ID and breaks clients using that app ID; application registration name and description restore is available for nonempty changes, while creation and all other application operations remain blocked in this release.

| Operation | Available subset or reason it stays blocked |
| --- | --- |
| Cloud users | Create a disabled member with display name, alias and UPN. Restore an existing cloud member's display name only. Other profile properties and account state remain unchanged. Synced and formerly synced users are refused. |
| Manager | Assign the saved manager as an individually resolved user relationship. Unresolved or protected users block that row. No manager is removed merely because the backup has none. |
| Static security groups | Create the directory object with fresh proof of a tenant-wide Groups Administrator or Global Administrator assignment, and restore its nonempty description. Clearing a description remains blocked because a live null restore did not consistently match read-back. Non-admin creation is refused because Microsoft can implicitly add the caller as an owner. Group settings, licensing and other properties are not replayed. |
| Members and owners | Add missing user principals to static, non-role-assignable security groups by default. Each row shows the principal name/type, resource, action and scope. Nested groups and service principals have no admitted live contract. |
| Exact membership and ownership | Separate choices for this group only. Every member removal needs its own approval and is limited to ordinary security groups. Conditional Access targeted-group removals are blocked because they can affect policy enforcement; remove those members in Microsoft Entra. Owner removal remains blocked after intermittent live refusals, including HTTP 400. Only the admitted user relationships can be written. Current members are read through beta so service principals are not silently omitted from comparison. Unsupported rows stay blocked. |
| Recycle recovery | Live user and group restores kept the object ID. Production remains blocked because inherited relationships and account state need a complete delegated safety review. |
| Account state, guests and licenses | Activation, invitations and license assignments were outside the approved lab scope and remain blocked. No automatic license retry occurs. |
| Microsoft 365 groups | Creation and member round trips worked in the lab, but owner removal returned 400. This variant stays blocked. Even a future directory restore would not recover Teams, SharePoint or mailbox content. |
| Dynamic rules | Paused fixture rules are tested separately. Production remains blocked because safe future beneficiaries have not been established. Dynamic members are never written directly. |
| Role-assignable and Conditional Access excluded groups | Require privileged and security-response review, and remain blocked until delegated indirect-beneficiary safety is verified. Lab role-assignable creation never assigned a role. |

After the object exists, choose **Relationships**. Preview pages contain up to 50 differences and execute approved rows in batches of 20. Every row needs its individual approval. The complete relationship difference is saved once in bounded records. Next-page previews use that saved inventory and resolve only the current page, including after restarting the app. Sensitive previews also show separate privileged and security-response approvals. Blocked rows explain their reason and cannot be approved. The signed-in admin, connected registration and designated recovery accounts are protected.

Copy the saved page ID to resume after restarting the app, open the same backup object and select **Resume saved page** with that ID. Reapprove the original selection. **Cancel directory restore** is available only for the executing page, including while its restore request loads the backup. Cancellation keeps that page ID visible so you can resume it, confirm its results or discard it once uncertain results are resolved. It interrupts throttle waits and stops unsent work and retries. A write already sent to Microsoft Graph finishes under its transport timeout so its result and any returned create ID can be saved. A definitely throttled attempt can resume without reconciliation; an unanswered in-flight request must first be reconciled. A changed tenant state requires a new preview. An unanswered create cannot be retried by starting another run. Group aliases are not unique, so an unanswered group create stays uncertain until its returned identity can be established; no automatic second create is sent.

A confirmed HTTP 429 response means the request was not applied, including when a safety read is throttled before a write. The result shows **Throttled by Microsoft Graph** and the earliest retry time. The page keeps its lock and Retry-After deadline across cancellation and restart. A throttled read-back or saved-page actor lookup keeps the dispatched result uncertain and saves the deadline on the live object. Uncertain results also show their saved retry time. Saving a retry deadline retries each of the journal and coordinator records once. If storage remains unavailable, the page keeps its lock and recovers the deadline from the record that was saved before releasing ownership. Users, Groups and Applications also retain attempt-bound retry publications and actor-read deadlines in memory during the same session; the saved deadline must be flushed before another same-object request can proceed. A deadline extended by another page during final checks also defers the approved row. Resuming repeats the final safety checks. A newer preview cannot replace or invalidate that page. Updates and relationship changes lock the resolved live object ID, including recreated objects referenced by newer backups.

Temporary safety-read failures (HTTP 408, 429, 5xx, timeout or network errors) leave the row deferred. Resume keeps the original selected rows and approvals and repeats their safety checks. Rows waiting behind an uncertain change to the same object also remain deferred and can resume after that result is confirmed. Drift and policy refusals require a new review. Relationship rows already matching the desired state cannot be selected for execution.

When you open **Review directory restore**, or **Saved directory restores** on the Restore tab, **Your unfinished saved restores** lists the saved pages that the signed-in admin and connection started in this tenant. The list is read from this device without contacting Microsoft Graph. A page stays listed while it has unresolved rows, and also while it still holds object locks after its rows finished, until its cursor and lock cleanup completes. The list refreshes after each saved-page action.

Microsoft Entra replicates new objects with a delay. Within 30 minutes after TenuVault acknowledged its own create of a user or group, a not-found answer for that object defers the row instead of failing it. This covers a write and the required safety reads of the relationship's group, managed user or principal. No write is sent for a deferred row. Resume after a few seconds to repeat the checks. Outside that window, or for objects TenuVault did not create, a missing object still requires a new preview. When Microsoft Graph asks for a new sign-in to satisfy Conditional Access (a claims challenge), on a write or a safety read, the row is deferred with that message. If the challenge comes while TenuVault reads the signed-in admin before any row runs, the action stops with the same message. Sign in again and resume.

Use **Discard saved restore** to abandon a saved page with no uncertain steps. Discard permanently prevents every batch of that page from sending and releases its locks in one durable change. It does not undo applied changes or shorten Microsoft Graph's Retry-After deadline. Discard is unavailable during execution or while a dispatched result is uncertain.

Uncertain means a request was dispatched but its result was not confirmed, for example after a timeout, network failure or HTTP 408 or 5xx. The UI says the result is being confirmed. On the Restore tab, enter the saved page ID under **Saved directory restores** and select **Confirm saved page results** to read back the journal's target identity and approved values. This action works even if retention deleted every backup, and remains available after restore opt-out. It never sends a mutation. A unique matching read-back marks the change applied. Empty lookups, repeated old values and ambiguous identities remain uncertain because the existing consistency rules do not prove the request failed. The lock stays held. Created IDs are saved in the journal and recovered into mappings before a new preview decides to create, preventing a second create after an interrupted mapping save. Saving a confirmed result is retried once. If storage remains unavailable, the durable unanswered marker and object lock remain held, and the acknowledged result is retained in memory for same-session save retries. Unreadable or conflicting saved coordinator state refuses the affected object with a clear error; damaged records for unrelated objects do not block its restore.

Users, Groups and Applications require both their enabled area and Backup and restore access at preview and immediately before every write. Read-only confirmation remains available after opting out.

Use **Preview next page** to continue beyond the current page, including blocked rows. Once a page is complete, preview relationships again for remaining differences. Completed differences are omitted. Partial results describe failed or unanswered rows and never promise rollback. Directory journals, preimages, approval bindings and ID mappings use encrypted partitioned storage on this device. Directory saved pages are resumed here rather than from the configuration history panel.

The lab uses unique TV06-TEST- names per run, disabled users and relationships only between those fixtures. It soft-deletes every test group and permanently removes test users. Under the owner's cleanup policy, deleted groups remain until Entra expires them after 30 days. Later runs list those groups with deletion dates and never restore an earlier run's groups.

Group link restore also refuses a resource with any current directory membership, including parent groups, directory roles and administrative units. This avoids granting inherited privilege through an unverified ancestor. The lookup uses existing group read access.

Exact member removal is not performed for groups referenced by Conditional Access `includeGroups` or `excludeGroups`. Membership changes can affect policy enforcement, and concurrent edits or replication delay prevent TenuVault from establishing a safe remaining membership. The removal row is blocked with instructions to remove the member in Microsoft Entra. Targeting is read at preview and again before each write, including throttle retries. Unreadable or incomplete policy targeting also blocks removal. Exact member removal from ordinary security groups remains available with individual approval. Member additions, owner additions and nonempty description changes retain their existing admission checks; the existing restrictions on excluded groups remain.

User display-name and manager changes are blocked when Conditional Access group targeting or exclusions exist or cannot be completely read. Their dynamic-membership effects need a separate verified review. Every access addition and manager change also has separate privilege and security-response approvals.

## App registrations, enterprise apps and consent

Open an owned backup and choose **Review directory restore** under Applications, ServicePrincipals or OAuth2PermissionGrants. The separate review admits only operations with matching documentation, fixture read-back and production integration tests. Application registrations support nonempty displayName and description updates. Other metadata fields and clearing names or descriptions remain blocked. These operations are never included in restore all.

TenuVault checks for changes in a final read, but another admin's edit to the same field in the moment between that read and TenuVault's write can be overwritten. These directory writes do not use If-Match. Coordinate edits with other admins during a restore. Exact member removal for Conditional Access targeted groups is blocked as described above.

The 30 minute consistency rule applies only when confirming TenuVault's own uncertain relationship writes. If its journal records an acknowledged write in the opposite direction for the same member and object within 30 minutes, a matching read-back remains uncertain until that window passes. This applies to both additions and removals and covers [Microsoft Entra replication delay](https://devblogs.microsoft.com/identity/designing-for-eventual-consistency-for-microsoft-entra/). The window is TenuVault's bounded confirmation policy, not a Microsoft replication guarantee; read-back never acknowledges a write or restarts the window. An acknowledged result is retained across same-session save retries so a later point read cannot downgrade it. Preview reads can still be stale after TenuVault's own write; run a fresh preview when needed. Other admins' changes remain subject to the concurrency limitation above.

Recreating an app registration generates a **new app ID**. This breaks every client that uses the old app ID, including sign-in configuration, scripts and dependent applications. The preview checks the recycle bin first. Recycle recovery can preserve the original object ID and app ID, but can also revive credentials and access. It remains blocked until all recovered state and relationships can be completely verified. A deleted identity is never bypassed by recreation. Restoring an application does not automatically restore its enterprise app.

An enterprise app candidate uses its app ID. A gallery app requires its original application template, never a name match. Current backups do not retain verified template provenance, so gallery recreation has a specific blocker. SAML signing keys, provisioning secrets, application secrets, private keys and federated identity credentials are never restored. Set up single sign-on and provisioning again only when rebuilding a missing app or recovering missing configuration. Name and description updates do not require this. Microsoft first-party enterprise apps and synchronized identities are never restorable.

Delegated consent remains blocked after inconsistent live lifecycle results. One complete create, merge, delete and recreate cycle matched, but a later deletion returned HTTP 400. Each staged grant has its own preview row and approval. App role assignments remain blocked after a live recreation attempt returned HTTP 400, despite matching creation and deletion read-back. Enterprise app metadata also remains blocked after HTTP 400 during the name and description round trip. Owner rows remain blocked: the live lab verifies only service-principal owners, while the production resolver handles users. Typed service-principal owner mappings and a matching user-owner live contract are not verified. Tenant-wide delegated grants require separate privileged and security-response approvals. Microsoft first-party resource apps remain blocked for consent and app roles. Reinstating removed access requires an additional security-response approval. Unresolved principals block their row. The signed-in admin, recovery accounts and the TenuVault connection remain protected from self-benefit.

Service-principal references resolve through the app IDs stored in the owned backup, never by replaying saved object IDs. A missing or ambiguous match blocks the relationship. Principal-specific delegated grants and user or group app role assignments remain blocked pending verified typed principal mappings. Raw saved user or group IDs are never replayed for these grants. Consent scopes merge with the current grant, adding only. Imported consent and assignments and all cross-tenant directory restores are refused. There is no bulk consent approval or exact-owner removal mode.

Token lifetime, claims mapping, home realm discovery and app management policy assignments reference the corresponding layer 8 configuration types. They are not replayed as app metadata. Bindings remain blocked until their typed configuration mappings and binding contracts are verified. Display names cannot uniquely reconcile a lost application or gallery create response, so those candidates remain blocked too. Non-gallery enterprise app creation also remains blocked because delegated caller ownership and inherited backing-app access have no verified safety contract.
