Selected Tenant settings and Authentication policies can be restored individually after an exact preview and a separate confirmation. Confirmation belongs to that restore run, tenant, signed-in admin and backup source. A new preview requires its own confirmation. If an earlier restore recreated a policy with a new ID, replacement previews and updates use that saved target mapping. All other Entra ID types and every Defender type remain backup-only. Cross-tenant copy and bulk restore of the new types remain refused. A documented Microsoft Graph API does not enable restore in TenuVault.

Conditional Access and Intune retain their existing restore behavior. See [Restore modes and assignments](/restore/modes/) for those policies.

## Protection before enabling restore

The restore safety boundary requires the signed-in admin for the connected tenant and registration. A Backup Reader, an app-only token or an unreadable token cannot write a new type. Missing write permissions require adding restore access from Services in Settings and signing in again.

Tenant settings restore access includes Application.Read.All to check token lifetime policy bindings. It grants no application writes. Each operation runs only the protections that its closed payload can affect. The four enabled subsets cannot remove protected identities, administrator roles, authentication methods or the connected registration. Token binding and non-default policy checks still run, and incomplete evidence blocks the affected policy.

The boundary protects the signed-in admin's own account, roles and authentication methods, designated recovery accounts and the connected TenuVault registration and enterprise app. Removing the last Global Administrator or Privileged Role Administrator is refused. An unresolved safety reference blocks the affected policy.

Members, owners and collection entries are added by default. Removing existing entries requires a choice for that individual policy. Consent grant changes merge scopes by default. Consent grants and role assignments from imported backups are refused. New Entra ID and Defender types cannot be copied to another tenant.

## Review recovery accounts and saved results

Open **Settings > Storage and recovery** and choose the restore history tenant. **Identity restore safety** shows the recovery account object IDs saved for that tenant. Enter one ID per line and select **Save recovery accounts**. TenuVault verifies that each is an enabled cloud member account before saving the choice on this device. An empty list designates no additional recovery accounts. The signed-in admin, connected registration and enterprise app remain protected.

## What partial means

Microsoft Graph offers no transaction across policies. A restore can finish some steps before another is blocked, cancelled or unanswered. A partial result records each policy's state and its dependencies. It does not promise that earlier changes were rolled back.

The journal captures only the objects a run touches before writing them. It binds the run to its tenant, signed-in admin and reviewed plan. A tenant change since preview requires a new preview. Created IDs and typed reference mappings persist across runs and are loaded before preview. Execution validates them again against the current journal. The journal retains the latest 1,000 settled runs, every unresolved run and every mapping independently. Dependencies with missing prerequisites or cycles are blocked for review. Replaced IDs referenced by Intune or Conditional Access require review of those policies. The reference scan keeps matches as it reads each policy and avoids script, image and secret sub-reads. Its overall budget is 500 requests, 30 seconds and 16 MiB of response data. The scan checks its read access before contacting Intune or Conditional Access. Missing access, cancellation, a failed read or any exceeded budget produces an incomplete-scan warning, never an empty-reference assurance. A completed configuration write can therefore still be reported as partial when unrelated reference reporting is unavailable.

A failed check before a mutation is sent is recorded as failed-before-send and permits a fresh preview. The send marker is saved immediately before the mutation request. A crash after that marker is conservative: the outcome stays uncertain even if the request had not yet left the device. An unanswered write must be read back before any retry. A matching object must have an unambiguous identity and match the sent properties. An empty or ambiguous lookup leaves the outcome uncertain, with no second create. Changing recovery accounts does not prevent read-only reconciliation. Current recovery protections apply before any later write. Restarting resumes from saved steps. Journal captures reject credential properties and credential values.

## Never restored

Secrets, passwords, OATH seeds, synchronization flags, domains, devices, Microsoft-managed and built-in objects are never recreated or overwritten by the new writer. Organizational contacts and Microsoft attack simulation content have no parent write contract. Attack simulation and training campaigns are never restored. Directory restore, memberships and privilege assignments require later implementation and review.

## Tenant settings and Authentication verification

Open a backup in Restore and expand its policy type. Enabled policies have **Review this configuration** beside their entry. Choose replacement of an existing policy or recreation of a missing policy, preview the exact changes, then select **Confirm and restore this policy**. Tenant singletons can only be replaced in place. Changing the operation or removal choice discards the preview. These controls are separate from selection and restore all.

| Type | Verified subset | Own confirmation |
| --- | --- | --- |
| Token lifetime policies | Create or update unbound, non-default Version 1 AccessTokenLifetime definitions | sign-in-policy |
| Activity-based timeout policies | Create or update non-default Version 1 ApplicationPolicies timeout definitions | sign-in-policy |
| Authentication flows | Replace self-service sign-up state | authentication |
| Company branding | Replace or clear the default username hint | configuration |

The matrix below records the final availability of every type and operation. Unsupported nested properties and child configuration are refused. The branding review explicitly restores only the default username hint from a full backup. Other branding fields, streams, layout and localizations stay as configured in the tenant. Clearing a username hint uses a null reset. Other policy types still refuse unsupported writable properties and child configuration.

Organization notification emails and phones, and the privacy profile, are never restored in 0.6. [Microsoft requires Organization.ReadWrite.All](https://learn.microsoft.com/en-us/graph/api/organization-update?view=graph-rest-1.0) for these changes, and TenuVault never requests that permission. Branding uses the separate least-privileged [OrganizationalBranding.ReadWrite.All permission](https://learn.microsoft.com/en-us/graph/api/organizationalbranding-update?view=graph-rest-1.0).

Permission grant policy metadata remains blocked after a live PATCH refusal (HTTP 400). Authorization policy, security defaults and authentication methods remain blocked. Their live verification used identical values only. Effective authentication-method targeting and usable methods for the signed-in admin are not yet established. Security defaults also have an unresolved least-privilege permission discrepancy. Admin consent request policy remains blocked because the lab's original zero-day duration does not satisfy the staged builder's restore-original contract. Directory settings and authentication contexts lack a verified safe lab fixture and write grant. Federation, certificate PKI, credential restrictions, token issuance, claims mapping and home realm discovery remain blocked. Domains, synchronization flags, credentials and hardware token seeds are never written.

The lab used an app-only adapter with an explicit path allowlist. It does not verify the product's signed-in actor, confirmation or journal boundary, which are covered by injected-fetch tests. Prefixed policies are removed in finally blocks. Singleton originals are saved outside the repository before changing them, restored and read back. Restoring a singleton original uses bounded retries with read-back reconciliation, including after a refused or lost recovery response. Final cleanup retries unresolved singleton recovery before any other mutation. A pending recovery file is kept until the original is verified and prevents another write run. Non-personal singleton originals and verified end values are recorded in a private run artifact outside the repository. Microsoft Graph can take time to propagate a create, update or delete; verification re-reads before deciding whether the result is confirmed. A failed or unanswered write is never treated as a promise of rollback. Notification values are never changed in the lab.

## External identities, Governance and Defender staging

These areas remain backup-only in phase 1. Restore access adds no write permissions for their blocked types. The endpoint matrix below shows a reason for every type, including the configuration side of Roles and PIM. Current Microsoft documentation and a successful live lab lifecycle must agree before an operation becomes available. No live writes have run for this phase.

The staged closed subsets are cross-tenant policy display name, the external-identities leave setting, custom user-flow attributes, unpublished access-package catalogs hidden from external users, the access-review ownership flag, the workflow schedule interval, disabled lifecycle workflow metadata and disabled Defender detection rules. Catalog writes still have no exact local-index match. Their documentation alone cannot enable restore. Candidate tests temporarily admit contracts only inside their isolated test process.

Cross-tenant access requires its own confirmation. Default and partner settings remain blocked because their selectors and the signed-in admin's tenant relationships cannot yet be resolved safely. A default that could block those relationships is explicitly identified as a lock-out risk. The prepared lab harness never writes defaults, partners, trust or synchronization settings. It uses identical values for the external-identities leave setting and workflow scheduling. Parent display-name and review-ownership changes retain a durable original and recover it with bounded retries and read-back before another mutation.

Lifecycle workflow updates always set both `isEnabled` and `isSchedulingEnabled` to false. Workflow creation remains blocked until recycle-bin-first recovery, task schemas and reconciliation are verified. Defender rule candidates always set `status` to `disabled`. They accept only a closed query, schedule and alert-template subset, with no automated response actions. Deprecated response-action properties and unsupported children are refused. Activation requires a separate approval and is not implemented by this restore path. Automatic-result access reviews remain blocked because disabling result application alone does not prevent a newly scheduled review from sending notifications.

Identity-provider and API-connector secrets are never restored and must be entered again. Their secret-free create contracts remain unverified, so those types stay blocked. Attack simulations, automations, training campaigns and their content are never restored. Built-in roles and attributes stay protected. Administrative-unit recreation remains blocked pending recycle-bin-first recovery; memberships are excluded. Attribute sets and security-attribute definitions have no delete lifecycle for safe lab cleanup and remain blocked. PIM rule schemas, privileged references, sensor settings, workbook method discrepancies and notification-bearing email policies also remain blocked with their specific reasons in the matrix.

The prepared lab harness is separate from the product writer. It only accepts the approved lab tenant and application, uses an explicit collection and path allowlist, creates `TV06-TEST-` objects, reads back each change, restores original configuration and attempts cleanup even after a lost response or refusal. Disabled detection fixtures use a query that matches no events and contain no response actions. No workflow, review, email, simulation, response action or external endpoint is executed. Application lab grants do not prove delegated production authorization. The production-service tests separately enforce each candidate's generated area scopes, exact confirmation, journal and applicable protections.
